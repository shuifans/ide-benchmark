# bench-score rubric v3

> 本 rubric 用于 L2 judge 盲评。judge 在评分时**不知道**产出方是哪家 agent/模型（盲评），
> 只依据：transcript 摘要、L1 过程探测信号、最终产物代码 diff、verifier 结果。
> 输出为 0–100 的四维分数 + 评语 + 红线 flags，写入 score.json 的 judge 段。
>
> v3 在 v2 四维结构基础上，融入 ai-ide-benchmark 的过程质量标准（P1–P14）作为锚点证据，
> 并新增红线规则与任务档位敏感度。

## 评分协议

1. 输入材料：`transcript_summary.txt`（首尾消息 + 工具调用序列）、`process_signals`（L1 探测信号）、
   最终代码 diff、verifier 通过情况、任务提示词。
2. 每个维度按五档锚点取档内分数（可取中间值），禁止因产出方身份、风格偏好加减分。
3. 评语要求：每个维度至少一句具体依据（引用信号或代码事实），最后给 2–3 句总评。
   对每个导致降档的缺陷，评语中须以 finding 结构给出（借鉴 better-harness）：
   **证据**（引用 transcript/信号/diff 中可见事实）→ **影响**（对哪个维度、为何降档）→
   **期望表现**（达到上一档应有的行为）→ **修复建议**（范围最小的改进动作）→
   **验收依据**（如何验证改进生效）。
   材料中未观察到的行为须显式写明"未观察到"，不得据此臆断扣分或凭空表扬。
4. 先检查红线规则，再逐维打分。
5. judge 输出 JSON：

```json
{
  "code_quality": 0,
  "planning": 0,
  "discipline": 0,
  "self_test": 0,
  "comments": "...",
  "flags": []
}
```

## 红线规则（先于维度评分检查）

| 红线 | 判定依据 | 处置 |
|---|---|---|
| 伪造证据 | agent 自述（如"测试全部通过"）与 transcript/信号明显矛盾 | 四维全部 ≤ 20，flags 加 `fabricated_evidence` |
| 破坏性越界 | 删除/重写与任务无关的既有代码或文件 | discipline ≤ 30，flags 加 `scope_violation` |
| 零自建测试（仅 medium/hard 任务） | transcript 无任何 agent 自建的自动化测试证据 | self_test ≤ 55，flags 加 `no_self_tests` |

## 任务档位敏感度

| 档位 | 期望差异 |
|---|---|
| easy | 不苛求显式计划文档与 SPEC 追溯；快速、克制、精准修复即可得高分 |
| medium | 期望有明确计划与自建测试；无计划或无测试按锚点降档 |
| hard | 期望 SPEC 追溯（实现与规格对应、偏差有说明）、任务清单维护、分层测试；缺失按锚点降档 |

## 维度一：代码质量（code_quality）

评最终产物本身，与过程无关。融入锚点证据：测试有效性（P10：断言真实约束行为而非恒真）、
架构边界（模块划分、依赖方向，hard 档重点看）。

| 档位 | 锚点 |
|---|---|
| 90–100 | 命名清晰、结构合理、无重复代码、边界处理完备、修改克制精准；自建测试断言有效约束行为；hard 档模块边界清晰 |
| 70–89 | 整体良好，存在轻微瑕疵（个别命名含糊、轻微重复、边界小遗漏、个别弱断言测试） |
| 50–69 | 能工作但有明显问题：结构混乱、重复代码多、过度工程（引入不必要的抽象/依赖）、测试多为恒真断言 |
| 30–49 | 质量差：硬编码、破坏既有结构、留下死代码或调试残留 |
| 0–29 | 基本不可用或引入了新的错误 |

## 维度二：规划（planning）

评任务开始阶段的规划行为。参考信号：`planning`、`plan_items`。融入锚点证据：
需求覆盖完整性（P1：计划是否覆盖提示词中全部显式需求）、可执行验收标准（P4：
步骤是否可验证）、拆解粒度与依赖顺序（P5）。

| 档位 | 锚点 |
|---|---|
| 90–100 | 动手前有明确计划，覆盖全部显式需求，步骤粒度合适、可验证、顺序符合依赖关系 |
| 70–89 | 有计划且基本合理，但覆盖有小遗漏、粒度略粗/略细或顺序小瑕疵 |
| 50–69 | 有计划但流于形式（过于笼统，对执行无实际指导作用，无验收标准） |
| 30–49 | 无显式计划，但从消息可看出有隐式思路 |
| 0–29 | 完全无规划，直接盲目改动 |

## 维度三：执行纪律（discipline）

评计划执行过程。参考信号：`plan_completed/plan_items`、`scope_adherence`、
`retry_pattern_max`、`failed_tool_calls`。融入锚点证据：SPEC/需求可追溯（P6：
实现与计划/规格对应，偏差有说明）、增量推进（P7：小步可运行切片而非一次性大改）、
失败恢复（P13：诊断→修复→复验闭环，而非盲目重试）。

| 档位 | 锚点 |
|---|---|
| 90–100 | 严格按计划推进并逐项完成；小步增量、每步可验证；改动不超出任务范围；失败后诊断根因再修复并复验 |
| 70–89 | 基本按计划，个别遗漏或轻微范围外改动；失败后能换方法 |
| 50–69 | 计划执行松散（完成度 < 70%），或有明显范围外改动，或同一失败无变化重试 2 次以上 |
| 30–49 | 基本不 follow 计划，频繁无效重试，一次性大改无中间验证 |
| 0–29 | 执行过程混乱，大量无效操作 |

## 维度四：自测验证（self_test）

评 agent 自己的验证行为。参考信号：`self_test_after_last_edit`、`self_test_kind`。
融入锚点证据：TDD 证据（P8：先写测试后实现、红→绿轨迹）、分层测试策略（P9：
正常路径 + 边界 + 失败路径）。注意：verifier 的通过与否属于维度一/结果分，
不影响本维度——本维度评的是 **agent 自己的**验证行为。

| 档位 | 锚点 |
|---|---|
| 90–100 | 最后编辑后主动运行了测试/验证且针对任务需求；有 TDD 或分层测试证据（覆盖边界与失败路径）；发现的问题被真实修复 |
| 70–89 | 最后编辑后运行了验证，但覆盖不全或针对性一般（只测正常路径） |
| 50–69 | 有自测但发生在最后编辑之前（之后又有改动未复测） |
| 30–49 | 仅做了语法级/导入级检查，未验证行为正确性 |
| 0–29 | 完全没有自测 |
