# bench-score rubric v2

> 本 rubric 用于 L2 judge 盲评。judge 在评分时**不知道**产出方是哪家 agent/模型（盲评），
> 只依据：transcript 摘要、L1 过程探测信号、最终产物代码、verifier 结果。
> 输出为 0–100 的四维分数 + 评语，写入 score.json 的 judge 段。

## 评分协议

1. 输入材料：`transcript_summary.txt`（首尾消息 + 工具调用序列）、`process_signals`（L1 探测信号）、
   `work/` 目录最终代码、verifier 通过情况。
2. 每个维度按下述五档锚点取档内分数（可取中间值），禁止因产物方身份、风格偏好加减分。
3. 评语要求：每个维度至少一句具体依据（引用信号或代码事实），最后给 2–3 句总评。
4. judge 输出 JSON：

```json
{
  "judge": {
    "model": "<judge 模型名>",
    "rubric_version": "v2",
    "blind": true,
    "scores": {
      "code_quality": 0,
      "planning": 0,
      "discipline": 0,
      "self_test": 0,
      "comments": "..."
    }
  }
}
```

## 维度一：代码质量（code_quality）

评最终产物本身，与过程无关。

| 档位 | 锚点 |
|---|---|
| 90–100 | 命名清晰、结构合理、无重复代码、边界处理完备、修改克制精准 |
| 70–89 | 整体良好，存在轻微瑕疵（个别命名含糊、轻微重复、边界小遗漏） |
| 50–69 | 能工作但有明显问题：结构混乱、重复代码多、过度工程（引入不必要的抽象/依赖） |
| 30–49 | 质量差：硬编码、破坏既有结构、留下死代码或调试残留 |
| 0–29 | 基本不可用或引入了新的错误 |

## 维度二：规划（planning）

评任务开始阶段的规划行为。参考信号：`planning`、`plan_items`。

| 档位 | 锚点 |
|---|---|
| 90–100 | 动手前有明确计划，步骤粒度合适、顺序合理、与任务需求匹配 |
| 70–89 | 有计划且基本合理，但粒度略粗/略细或顺序小瑕疵 |
| 50–69 | 有计划但流于形式（过于笼统，对执行无实际指导作用） |
| 30–49 | 无显式计划，但从消息可看出有隐式思路 |
| 0–29 | 完全无规划，直接盲目改动 |

## 维度三：执行纪律（discipline）

评计划执行过程。参考信号：`plan_completed/plan_items`、`scope_adherence`、`retry_pattern_max`、`failed_tool_calls`。

| 档位 | 锚点 |
|---|---|
| 90–100 | 严格按计划推进并逐项完成；改动不超出任务范围；失败后能有效调整策略 |
| 70–89 | 基本按计划，个别遗漏或轻微范围外改动；失败后能换方法 |
| 50–69 | 计划执行松散（完成度 < 70%），或有明显范围外改动，或同一失败无变化重试 2 次以上 |
| 30–49 | 基本不follow计划，频繁无效重试 |
| 0–29 | 执行过程混乱，大量无效操作 |

## 维度四：结束后自测（self_test）

评收尾验证行为。参考信号：`self_test_after_last_edit`；并结合 transcript 判断自测是否针对需求、
失败后是否真实修复。注意：verifier 的通过与否属于维度一/结果分，不影响本维度——本维度评的是
**agent 自己的**验证行为。

| 档位 | 锚点 |
|---|---|
| 90–100 | 最后编辑后主动运行了测试/验证，且验证针对任务需求；发现的问题被真实修复 |
| 70–89 | 最后编辑后运行了验证，但覆盖不全或针对性一般 |
| 50–69 | 有自测但发生在最后编辑之前（之后又有改动未复测） |
| 30–49 | 仅做了语法级/导入级检查，未验证行为正确性 |
| 0–29 | 完全没有自测 |
